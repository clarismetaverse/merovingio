# Native Score fan-out for bridge ranking and Generic Space bindings

Parent: b192822. Branch: codex/native-score-bridge-generic-search. Main and v0.9/v1.0 and all temporal experiments preserved. Model jev-1.14.0, direct HTTP only through GitHub Actions.

## Two related user requests

Use existing Mental Spaces and Generic Spaces as scoring dimensions to rank possible bridges; also search known/new Generic Space candidates. Evaluate whether speculative fan-out can compare many schemas without repeatedly sending the common workspace. This is a bounded native-Score prototype, not a complete Euclid corpus or a 2000-schema stress test.

The repo currently contains ten curated Generic Space memory entries and five proposition records. The full real memory is used. Two further schemas are generated by code: an interface shared by two polygonal regions, and a competing congruent-region hypothesis. Novel proposals are not freely invented by Jev; they are explicit finite-grammar hypotheses scored by Jev and independently checked against the constructed graph. No memory entry is automatically written back or promoted into a theorem.

## Shared workspace and speculative questions

Two scalene triangle layouts, two label/order repetitions. Five hypothetical bridges: three vertex-to-opposite-edge connectors, a connector between interior points of two sides, and a no-change negative control. The initial diagram is shared, along with code-extracted points, new segments and hypothetical region boundaries. Images have object letters, never method names, score labels or answers. Anonymous candidate labels and question order change by repeat. Existing MS are the three angular fans and three side carriers. Two existing GS dimensions concern a common carrier between triangles and one carrier with distinct participations.

For every bridge ask eight native Score questions against these existing spaces. For every bridge and each of 12 schema candidates ask three native Scores: local fit in the first induced region, local fit in the second, and cross-space alignment with premises. Five bridges x (8 + 12 x 3) = 220 real Score questions in ONE request. All questions are evaluated speculatively before knowing which bridge or schema will be used; code selects relevant results afterward.

The first attempt duplicated each schema description across its speculative questions and returned HTTP 400; sanitized diagnostics detected a token-related validation message. The optimized pilot puts the twelve short schemas once in a shared state dictionary and each question references its schema alias. Both the small and full request contain that identical shared library. This avoids repeated descriptions. For a much larger catalog, shard the library or put each schema in its question so that a giant global library does not exceed the per-question context. The current small shared catalog is not a claim that 2000 full schemas fit in state. Scores use four descriptive levels (native values 0..3); preserve native score, confidence, probability distribution, optional numeric reliability and usage. Native Score is not replaced by an external numeric answer. Code normalizes by 3 and constructs composites.

## Bridge priority profiles

Scores are reusable; priority weights are not sent to Jev and are not answers embedded in prompts. Profile focus_C weights fan_C=.35, side_AB=.35, shared-triangle GS=.2, polyrole GS=.1. Profile focus_A uses fan_A and side_BC with the same other weights. Each sums to one. The independent reference changes from the C connector to the A connector. This is an explicit engineering preference, not universal bridge quality. All axis scores and raw rankings stay visible. Geometric admissibility only rejects no-change/no-region candidates, not candidates that disagree with the preferred objective. Select a bridge only for a unique best admissible composite >= .6; keep ties and abstentions explicit.

Region extraction is independently computed by inserting connector endpoints into the host boundary and walking both boundary paths. Check positive areas, shared connector identity and host area conservation. Ordinal reference axes are code-derived from incidences and region types. They are a benchmark reference under these rubrics, not an objective universal measure of creativity.

## Generic Space selection and proposal verification

A schema's model-supported binding requires mean normalized local/local/alignment score >= .75 and every axis >= 2/3. Multiple GS may coexist; no forced exclusive Choice. Preserve model-supported results before any independent gate. The independent checker then tests whether the claimed structural binding is instantiated: two triangular cells for the historical double-triangle schema, a shared interface for polyrole/interface schemas, and independently established metric/circle/distinct-genealogy premises for the corresponding memories. Missing premises cannot be compensated by high unrelated model scores.

The congruent-region proposal is rejected on all current fixtures (unequal region areas and no congruence certificate). The theorem memories remain conditional templates; an uninstantiated premise here does not make the theorem or schema invalid universally. The no-change control has no new region pair. Report raw supported bindings, unsupported bindings above the model threshold, and separately accepted checked bindings. Acceptance by a deterministic gate is not a Jev precision claim or a formal proof. A new shared-interface binding is a verified candidate from the supplied grammar, not autonomous open-ended discovery.

## Fan-out cost/latency probe

For each layout/repetition also call the SAME state/assets with only the eight bridge scores for the C connector. Compare 8 questions versus 220 on unchanged common context and unchanged overlapping questions. Four serial pairs, counterbalanced small-first/full-first, eight total API calls and up to 912 native Score answers. No concurrent HTTP calls in this timing experiment and no automatic retries. Report actual wall time, usage, body bytes and overlap score changes. Four pairs are descriptive, not a universal batching speed guarantee.

The 200/2000 cases in results are sizing-only scenarios. One coarse Score per schema gives 200/2000 questions. Five bridge candidates x three dimensions x 200/2000 schemas gives 3000/30000 questions. An illustrative 80 tokens per coarse question gives 16k/160k extra tokens before shared state; this is not a tokenizer estimate, live measurement or a claim that 2000 theorem schemas exist in this repo. No repeated dummy schemas are passed off as distinct theorems.

Official docs checked: https://docs.typesafe.ai/patterns/fan-out ; https://docs.typesafe.ai/primitives/score ; https://docs.typesafe.ai/patterns/composite-scoring ; https://docs.typesafe.ai/models ; https://docs.typesafe.ai/cookbooks/parallel_questions . Current documented defaults: 64k combined request context, 32k state plus a single question, no separate question-count cap; 32 MiB JSON body. Long context can raise limits but is slower and less accurate according to the vendor. It is not enabled here. Published examples do not establish flat latency at 2000 schemas.
